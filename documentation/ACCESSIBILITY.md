# Accessibility

NOFO Builder turns finalized Word documents into Notices of Funding Opportunity
(NOFOs) that the public uses to apply for federal funding. This page states the
accessibility standards that apply, what Builder does to support them, how output
is checked, what is known to be missing, and how to report a problem.

## Standards

| Surface | Audience | Required | Goal |
| --- | --- | --- | --- |
| Published NOFO PDFs | Applicants and the public | [Section 508](https://www.section508.gov/); a tagged PDF | WCAG 2.2 Level AA where practical |
| NOFO Builder and Composer web app | HHS designers and writers | Section 508 | WCAG 2.2 Level AA where practical |

- **Section 508** applies to HHS electronic content and information technology.
  The [Revised 508 Standards](https://www.access-board.gov/ict/) incorporate
  **WCAG 2.0 Level A and AA**, so WCAG 2.0 AA is the minimum for both surfaces.
- **WCAG 2.2 Level AA** is the current W3C Recommendation. It includes the
  WCAG 2.0 and 2.1 AA success criteria, so meeting it also meets the minimum.
- **Design standards** for published NOFOs come from the HHS Office of Grants.
  [DESIGN_STANDARDS.md](DESIGN_STANDARDS.md) reproduces selected guidance and its
  before-publication checklist; the official standards govern.

## What Builder does

These behaviors support accessible output. None of them alone establishes that
a PDF is accessible.

- **Tagged PDF request.** PDFs are generated by DocRaptor (Prince) with the
  `PDF/UA-1` profile and print styles (`nofos/nofos/pdf_service.py`). Requesting
  the profile, and testing that request, does not verify the PDF's tags or reading
  order. See [Validate the PDF](SCALABLE_NOFO_DESIGN_SYSTEM.md#4-validate-the-pdf-not-just-the-authoring-screen).
  Prince was chosen partly because it produces tagged PDFs; see the
  [PDF generation library ADR](adr/2023-12-07-pdf-generation-library.md).
- **Structure from the source.** Import keeps Word headings, lists and tables as
  structure rather than visual formatting. The automatic rules are cataloged in
  [IMPORT_RULES.md](IMPORT_RULES.md).
- **Missing alt text is marked.** An imported image with no alt text gets empty
  alt text and an internal marker
  ([IMPORT-033](IMPORT_RULES.md#import-033--missing-alt-text-backfill)). Screen
  readers treat empty alt text as decorative, so an image that conveys
  information still needs an author to add alt text.
- **Before publishing checks.** The NOFO edit page flags heading levels, broken
  links, missing link destinations, external links, endnotes, PDF metadata,
  list numbering and leftover template instructions. Each has an editor task,
  for example [TASK-HEADING-LEVEL](EDITOR_TASKS.md#task-heading-level) and
  [TASK-PDF-METADATA](EDITOR_TASKS.md#task-pdf-metadata). These checks flag
  problems; they do not check color contrast or PDF reading order.
- **Alt text and metadata fields.** Editors can set cover image alt text
  ([TASK-COVER-ALT-TEXT](EDITOR_TASKS.md#task-cover-alt-text)) and the PDF
  author, subject and keywords.
- **Design system.** The web app uses the
  [U.S. Web Design System](https://designsystem.digital.gov/) components,
  landmarks and screen-reader-only labels, and NOFO themes are adapted from it.

## How output is checked

- **Authors and designers** check the final PDF against the
  [before you publish](DESIGN_STANDARDS.md#before-you-publish) checklist, after
  addressing the Builder checks above and previewing the PDF
  ([TASK-PREVIEW](EDITOR_TASKS.md#task-preview)).
- **Reviewers** follow [quality review and triage](QUALITY_REVIEW_AND_TRIAGE.md#review-design-accessibility).
  A selected checklist or visual inspection alone does not establish full
  accessibility compliance.
- **Automated PDF checks** are not part of Builder.
  [#980](https://github.com/HHS/simpler-grants-pdf-builder/issues/980) describes
  the current practice of exporting the PDF and running Adobe Acrobat Pro's
  accessibility checker, and evaluates in-product scanning. That spike is
  paused; reuse it rather than starting a separate scanner.
- [Section508.gov testing guidance](https://www.section508.gov/test/) describes
  manual and automated testing methods.

## Known gaps

- **No automated accessibility testing of the web app.** CI runs the Django
  test suite and security scans, but no axe or pa11y checks. The
  [Simpler Grants frontend](https://github.com/HHS/simpler-grants-gov) runs
  pa11y-ci and could serve as a model.
- **No automated PDF validation.** See #980 above.
- **Color contrast is not documented as reviewed** for each NOFO theme or for
  the web app. Builder does not check contrast.
- **Heading 7 is offered** in the subsection heading-level selector, but the
  design guidance limits structural headings to H1–H6. See the notes in
  [TASK-HEADING-LEVEL](EDITOR_TASKS.md#task-heading-level).
- **Output depends on the source.** Images without alt text, complex tables and
  typed list markers in the Word file need author fixes; see the
  [design standards](DESIGN_STANDARDS.md).

## Report a problem

- **Applicants and the public:** for a published NOFO that is hard to use with
  assistive technology, contact the agency contact listed in the NOFO. HHS also
  publishes an [accessibility page](https://www.hhs.gov/accessibility/index.html).
- **NOFO Builder users:** contact your grants policy office first. If more help
  is needed, contact the SimplerNOFOs team.
- **Product issues:** search existing issues, then open a
  [bug report](../.github/ISSUE_TEMPLATE/bug_report.md) or
  [feature request](../.github/ISSUE_TEMPLATE/feature_request.md) and ask for the
  existing `A11y` label. Describe the page or PDF element, what you expected, and
  the assistive technology and browser you used. Don't attach documents that
  aren't cleared for a public repository.

## For contributors

- Follow the [contribution workflow](CONTRIBUTION_WORKFLOW.md) and reuse
  [UI patterns](UI_PATTERNS.md) and USWDS components rather than custom widgets.
- Don't remove alt-text handling, heading checks or the `PDF/UA-1` render profile
  without recording the decision in [DECISIONS.md](DECISIONS.md) or an
  [ADR](adr/README.md).
- In a PR that changes templates, themes or PDF output, state how you checked
  accessibility (keyboard, screen reader, contrast, PDF checker) and mark
  anything not checked as not checked.
